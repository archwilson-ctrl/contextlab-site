AI 能協助寫程式，但真正決定專案品質的，往往不是 Prompt，而是一份清楚的規格文件（Specification）。

最近協助會計事務所處理營業稅（401）申報文件時，發現每期都需要從國稅局下載大量 PDF 檔，並且逐一重新命名，以符合公司內部的歸檔規則。

這個工作本身並不困難，但每兩個月都需要重複進行，而且檔案數量動輒數百份，不但耗時，也容易因人工操作而發生錯誤。

因此，我決定利用 AI 與 Python 開發一套 Windows 桌面工具，將整個流程自動化。

## 問題是什麼？

事務所同仁收到的 PDF 檔名格式通常如下：

```text
11504_12345678_營業人銷售額與稅額申報書(401)_.pdf
```

但事務所希望整理後的檔名能夠直接辨識客戶與申報期，例如：

```text
401表-某某公司-11503-04.pdf
```

若完全依靠人工修改，每一份都必須：

- 查看統一編號
- 查詢公司名稱
- 判斷申報月份
- 組合新的檔名
- 檢查是否重複

當檔案數量增加時，效率與正確性都會快速下降。

## 我的開發方式

這次並不是直接請 AI 寫程式，而是先完成一份完整的規格文件（Specification）。

我把需求拆成數個部分：

- 專案資訊
- 檔案來源
- PDF 命名規則
- Excel 欄位定義
- UI 規格
- 狀態定義
- 統計方式
- 例外處理
- 打包方式

這樣 AI 就能根據規格逐步完成程式，而不是依賴一次性的 Prompt。

## 為什麼要先寫 Spec？

很多人使用 AI 開發時，都是想到什麼就問什麼，例如：

```text
幫我寫一個批次改名工具。
```

AI 當然可以產生程式，但每修改一次需求，都可能需要重新生成大量程式碼。

如果先把需求整理成規格文件，就能讓 AI 更容易理解整個專案。

例如這次就明確定義了：

- PDF 檔名如何解析
- 月份如何換算
- 新檔名格式
- 重複檔名如何處理
- 哪些情況算成功
- 哪些情況需要略過

這些都屬於商業規則（Business Rules），也是最需要由人決定的部分。

## AI 負責寫程式，人負責定義規則

我認為 AI 開發最重要的分工是：

```text
人：定義需求、流程、規則
AI：撰寫程式、產生介面、補齊細節
人：驗證結果、持續修正規格
```

當規格愈完整，AI 的產出通常也愈穩定。

## 本次規格的重點

這份規格除了功能需求之外，也包含不少容易被忽略的細節，例如：

- 預覽模式，不直接修改檔案
- 執行前再次確認
- 自動處理重複檔名
- 高 DPI 顯示最佳化
- 統計成功、失敗與略過數量
- Windows 執行檔打包方式

這些都是使用者真正會遇到的情境，也是提高工具完成度的重要因素。

## 我的心得

很多人認為 AI 開發就是一直寫 Prompt。

但我越來越認為，一份好的規格文件，比一段厲害的 Prompt 更有價值。

Prompt 可以重寫，模型也會一直更新；但規格代表的是對業務流程的理解，是企業真正累積下來的知識。

因此，在 ContextLab 的實作中，我會盡量保留每一份 Spec、每一次需求拆解與設計思考。

因為真正能累積企業競爭力的，不是模型本身，而是那些被整理、定義並持續演進的 Context。
